# hifi-decode reference fixtures

Stage-by-stage output of the real Python `vhsdecode.hifi.HiFiDecode` code,
run against a deterministic synthetic RF signal. Used to validate the Rust
port stage-by-stage (see `/Users/hugo/.claude/plans/vectorized-meandering-toast.md`,
step 3/4) without needing a real capture.

## `synthetic_pal_vhs/`

Generated by `scripts/hifi-fixtures/generate_reference.py`. Signal: two FM
carriers (PAL VHS AFE parameters, 1.4/1.8 MHz, ±150 kHz deviation) at 8 MHz
RF sample rate, 50 ms, each carrier frequency-modulated by a known pure tone
(L: 1 kHz, R: 2 kHz) via continuous-phase integration (not a phase-modulated
approximation). Decoded with `demod_type=quadrature` (the default), PAL VHS,
stereo mode, DOC on, head-switch interpolation on, no auto-fine-tune, no
spectral NR — i.e. hifi-decode's default CLI behavior.

Regenerate with:

```bash
cd /Users/hugo/vhs-decode
.venv/bin/python3 /Users/hugo/tape-decode-rust/scripts/hifi-fixtures/generate_reference.py
```

### Known limitations of this fixture set

- **Clean signal only.** No injected dropouts or head-switch noise pulses,
  so stage 05 (DOC) and the noise-interpolation half of stage 06 are
  validated as no-ops here, not exercised on their actual job. Add an
  adversarial fixture (synthetic carrier-loss gap + a head-switch-like
  broadband pulse) when implementing/validating those two Rust stages
  specifically (plan steps 4.6/4.7).
- **Single continuous block**, not the real block-size/overlap chunking
  `main.py`'s driver does (`BLOCKS_PER_SECOND=2`, trimmed overlap margins).
  That chunking is a step-6 (concurrency) concern, orthogonal to per-stage
  DSP correctness — validate it separately via an end-to-end CLI comparison
  against the real `hifi-decode` binary on an actual multi-block capture
  (plan's Vérification, item 4), not against these fixtures.
- Verified against ground truth by checking the final stage's FFT peak
  lands exactly on the synthesized 1 kHz / 2 kHz tones, and that RMS
  amplitude is consistent with unit-amplitude sine input — not by any
  independent re-implementation, since the whole point is that this *is*
  the real Python decoder's own output.
